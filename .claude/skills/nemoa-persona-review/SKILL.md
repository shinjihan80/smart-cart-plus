# 네모아 페르소나 검토

## 목적

네모아의 특정 화면·기능·빌드를 **고객 10인 + 전문가 3인**의 고정된 시선으로 반복 검토하여,
매번 같은 기준으로 개선점을 뽑고 우선순위가 매겨진 수정 목록에 누적한다.

- 검토단(customer): C1~C10 — 20~50대, 나이대별 2~3인, 성격·상황 상이. "이 화면에서 내가 막히는 지점"을 찾는다.
- 전문단(expert): E1 기획 / E2 개발 / E3 디자인 — 원인 진단 + 해결안 제시.

## 언제 무엇을 읽나

| 상황 | 읽을 파일 |
|------|-----------|
| 페르소나 배정·상세 렌즈 확인 | `references/roster.md` |
| 산출물 형식·우선순위 기준 | `references/output-schema.md` |
| 과거 검토 결과·기존 수정 목록 | `docs/nemoa-review/수정목록.md` |

## 검토 절차 (에이전트 1인 기준)

1. **페르소나 로드** — 배정받은 키(C1~C10 또는 E1~E3)로 `references/roster.md`에서 자기 프로필을 읽는다. 그 사람이 되어 사고한다. 다른 페르소나의 시선은 쓰지 않는다.
2. **검토 대상 확인** — 오케스트레이터가 넘긴 대상(스크린샷 경로, URL, 빌드, 기능 설명서, diff)을 본다. 대상이 불명확하면 추측하지 말고 오케스트레이터에 되묻는다.
3. **렌즈 적용** — 프로필의 "반드시 확인" 항목을 하나씩 대조한다. "무시하는 것"에 해당하면 지적하지 않는다(그 페르소나는 신경 안 쓴다).
4. **발견 기록** — 발견마다 `references/output-schema.md`의 finding 레코드로 적는다. 근거(화면·문구·수치)를 반드시 인용한다. 추측성·일반론 금지 — "내 상황에서 구체적으로 무엇이 막히는가"만.
5. **전문단 추가 작업** — E1~E3는 각 발견에 원인 가설 + 해결안 + 예상 난이도(S/M/L)를 붙인다.
6. **자기 우선순위 제안** — 각 발견에 P0/P1/P2 추정치를 붙인다(최종 판정은 오케스트레이터).
7. **반환** — finding 레코드 배열만 반환한다. 서론·요약·인사말 없이.

## 핵심 원칙

- **페르소나 고정**: 배정된 1인의 시선만. C7(실용주의 가장)이 갑자기 디자인 톤을 논하지 않는다.
- **근거 인용 필수**: 모든 발견은 관찰된 화면·문구·숫자를 인용. "왠지 불편"은 반려.
- **중복 허용**: 여러 페르소나가 같은 문제를 짚어도 각자 기록한다(오케스트레이터가 병합하며 "제기자 수"가 우선순위 신호가 된다).
- **없는 기능 상상 금지**: 검토 대상에 실제로 보이는 것만. 아카이브 문서와 라이브 빌드가 다를 수 있으므로 대상으로 받은 것만 신뢰한다.
- **누적**: 최종 수정 목록은 기존 `docs/nemoa-review/수정목록.md`에 덮어쓰지 않고 병합(신규 ID 발급, 기존 항목 상태 갱신).

## 산출물

오케스트레이터는 전 페르소나의 finding을 병합해 다음을 만든다:
- `docs/nemoa-review/_workspace/` — 페르소나별 원본 finding (`{persona}_findings.md`)
- 통합 수정 목록 — P0/P1/P2 표 (ID·영역·수정내용·근거 페르소나·상태). 형식은 `references/output-schema.md`.
